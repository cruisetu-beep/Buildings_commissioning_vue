## 一、这个页面在解决什么

原 4.3 详情页「计算过程」被反馈**过于专业、看不懂**。解法是新建一个并存的 v2 页面，把计算过程从算法展示改成**判决书式叙事**：先说这栋楼怎么了，再给过程、核查方向、判据表、原始算法说明。

入口：4.1 清单卡片右下角「新版」小按钮 → `/result-v2/:id`；页面右上角「回旧版」。
**旧页 `/result/:id` 及其组件零改动，两版可同时打开对比。**

```
头部：楼名 + 编号 + 业态 + 命中统计   ← 全部并入一行
左栏：建筑信息 / 计量节点 / 规则命中总览（八类分组可折叠，计数分三级权重）
主栏：规则名 + 标签
      窗口 tab（!/✓/? 三态 + "N 个窗口 · M 个触发"，默认落在首个触发窗口）
      ⓪ 结论卡（常驻，三态配色）
      ① 计算过程与图表（默认展开）
      ② 建议核查（默认收起）
      ③ 判定依据（默认收起）
      ④ 算法与判定标准（默认收起，渲染后端 resultMd）
```

### 五种可视化的画法与理由

- **A 聚类**：三日日内曲线叠放（时刻为横轴）+ 一维分布（电耗为横轴、时刻仅用于摊开）。
  **不要**用温度做横轴——C01 等温窗口内温度恒等，旧版那个横轴是 `hour` 线性映射出来的构造值。
- **B 回归**：散点 + OLS 拟合线，横轴是逐点实测温度。拟合线在低温端落到负值不裁剪，那是拟合质量的信号。
- **C 日对**：归一化斜率图，所有节点从 Day A = 100% 出发，斜率即各自变化率。
  **不用分组柱状图**——C03 泵与主机绝对值差约 90 倍、C02 冷却塔与冷热站差 77 倍，小的那根柱在同轴上是看不见的线。
- **D 分布**：两个页签。「功率序列」折线 + 分日竖线 + 极值高亮；「分布」用后端 `distributionBuckets` 画直方图。
  **两个都要**——C06 的判据只由 max、min 两个点决定，只看直方图会漏掉极值落在哪。
- **E 作息**：24h 阶梯面积曲线。`pair` 两条（面积之比即残留率），`single` 一条 + 时段底纹 + 基准线。

逐时聚合值一律 `step: 'end'`，不用 `smooth`——平滑会插出数据里没有的弧度。

**`markArea` 在类目轴上「含末类目」**：覆盖 01:00–05:00（即第 1–4 小时）要写 `to: "04:00"`，不是 `"05:00"`。曾在 BC-S1 写错、右侧多画一小时（`6580da8` 已修）。

## 四、加一条新规则的流程

**先要真实 `F_ResultJSON` → 核对可复现性 → 定图 → 再写代码。**
踩过的：C01 按「聚类=散点图」画出假温度轴、D05 猜是 C 类实际是 E 类。

### ⚠ 同一 `type` 不代表同一结构，同一 `mode` 也不代表

| 情形 | 差异 |
|---|---|
| D05 vs AA-S2（同为 `mode: pair`） | 窗口结构 `workday/holiday` 对象 vs `sWindow`+`dateFrom/dateTo`；metrics `residualRate/groupThreshold/passed` vs `residual/threshold`（无 passed） |
| BA-S1 vs BC-S1（同为 `single`） | 分母一个是当日峰值、一个是白天时段均值 |
| C03 vs C02 vs C07（同为 `dayPair`） | `energyBreakdown.series` 分别是 2 / 3 / **1** 项（C07 后端预先合并了节点，曾因 `length < 2` 的守卫导致整条渲染不出图） |
| C06 vs C04（同为 `distribution`） | 字段名逐个相同，但 `maxMeanRatio` 一个是 max/min、一个是 max/mean，判据方向还相反 |

**解析器一律按 `metrics.algo` 分流；D 类没有 algo，只能按 `raw.ruleId` 写死。**

### 具体步骤

1. **先算一遍**：用 `hourlyProfiles` / `energyBreakdown` / `powerSeries` 手算后端的 metrics，确认能精确复现。四条规则的日总电耗字段有 4 倍缺陷（六·B），不复核就会照抄错数
2. `rule-narrative.js` 照现有常量写六个字段（`narrative/title/steps/foot/causes/readHint`）
3. 句式里的 `{xxx}` 对应 `RuleDetailAreaV2` 的 `vals`；新形态需在该组件里扩 `vals` 分支
4. 每个 `kind:"test"` 的 step 要给 `key`，并在 `stepPassed()` 补比较逻辑
5. 注册进 `NARRATIVES`（编号大小写/空格/连字符会自动归一化）
6. `causes` 两种写法：字符串数组（单一故障模式）或分组数组 `[{whenFalse, title, items}]`（多故障模式，按后端布尔筛选）。D02 用后者——两条判据对应完全不同的故障，混着显示会给错方向

**模板不支持条件分支。** 需要按数据方向改措辞的（如 AA-S3 的 `drop` 为负时应读作「反而上升」而非「降幅 -69.9%」），在 `vals` 里算好成一个字段再塞进句子。

### 新增类型要动的扩展点

解析器 + option builder 在 `viz-chart-options-v2.js`；`RuleDetailAreaV2.vue` 里要动 `vizKind` / `hasViz` / `VIEWS` / `render` / `vals` / `stepPassed` / 数据页签表格 / 纵轴名，共八处。

### ⚠⚠ `stepPassed` 的 key 必须全局唯一

**已经出过一次事故**：D05 和 AA-S2 都用了 `residual`，写成两个独立分支，后者被前者遮蔽。AA-S2/BA-S2 没有 `passed` 字段，`undefined === false` 得 `false`，**两条规则所有触发窗口的判定依据表都显示 ✕**，与结论卡的红色状态矛盾（`9a1fc99` 已修，合并为单分支：有 `passed` 取布尔，无则比阈值）。

**当时漏掉的原因：验证脚本自己复刻了判断逻辑，没调用真正的 `stepPassed`。** 现在的做法见第五节。

当前已用的 21 个 key：
`sil` `delta` `standby` `tempMatch` `residual` `frac` `ndr` `r2` `sr` `slope` `r` `meteo` `eta` `dr` `ratio` `cvLow` `rMaxMean` `meteoRange` `early` `mild` `lunchDrop`

`meteo` 由 C02/C07 共用——两者都读 `conditionPassed`，是同一逻辑，共用是对的。**其余不要共用。**

### A. C02 判据方向与其公式定义相反 【最高】

手册 264 行定义 Δη = (E_reject(A) − E_reject(B)) / E_reject(A)，**电耗下降时 Δη 为正**；判定准则却写「Δη ≥ −5%（即降幅不足 5%）触发」。按该定义「降幅不足 5%」应为 **Δη < 5%**。

现行条件除非逆势上涨超 5% 否则**恒成立**。实测窗口：湿球降 4.65℃、散热侧合计电耗降 25.3%（冷却塔更降 52.6%）——教科书式的正常响应，仍判「目标调适」。

**这是手册正文的错误。** 修法二选一：把分子改成 (E_B − E_A)，或把判据改成 Δη < 5%。

**已确认是孤例**：C07 的 Δr = (E_B − E_A)/E_A 下降为负、判据写 > −15%，**自洽**。差别只在分子前后顺序。

前端应对：C02 的 title 与 narrative 退到中性表述（「落入触发区间」），图上不画合格线。**方向厘清后要改的是 `title` 与 `req` 两处措辞**，位置已在常量注释里标出。

### B. 日总电耗字段普遍为逐时积分的 4.0000 倍 【高】

疑似 96 个 15 分钟读数直接求和未除以 4。已在**四条规则**复现：D05 (`eWork`/`eHol`)、AA-S2、BA-S2 (`eWork`/`eOther`)、AA-S1 (`eDay`/`eNight`)。

比值判据不受影响，但**绝对值当 kWh 显示会大 4 倍**。AA-S1 尤其危险：`eDay/10` 字面看是 kW，某窗口显示 16.8，实际只有 4.20。**前端一律回避这些字段**，真实 kW 由 `hourlyProfiles` 自算。

根因已确认：C06 的 `powerSeries` 是 96 个 **15 分钟**读数（3 日 × 8h × 4），而 `resultMd` 写「逐时」。

### C. `U2A00` 是子节点的父节点，指标定义重复计入 【高】

`modelNodes` 的 `parentNodeId` 明确：冷冻泵、冷却泵、冷却塔都挂在冷热站 `U2A00` 下。影响三条规则：

- **C02**：E_reject = U2A00 + U2A02 + U2A04 把冷却泵和冷却塔各算两遍，且 U2A00 占合计 **87–89%**，所谓「散热侧总电耗」实为整个冷热站。真散热侧（泵+塔）在实测窗口只降 11.8%，与 25.3% 差得远
- **C03**：把 `U2A00` 标为「冷水主机」当分母。若它实为含泵的冷热站总表，R 算的是「部分 ÷ 整体」
- **BA-S2**：`requiredNodeTypes` 三者相加同样重复

**请确认 `U2A00` 到底是主机还是冷热站总表。**

### D. BB-S1 的规则名与实现的算法不是一回事 【高】

`ruleName` 写「商场停业后主机泵下降极小」、`thresholdValue` 写「关店前后降幅<25%」，但 `judgmentStandard` / `resultMd` / `metrics.algo` **全都是清晨预冷判定**。

手册该节标题是「停业后主机泵功耗下降极小**与过度提早预冷**判定」——两件事合成一条规则，而「数学算式与步骤」**只写了预冷那半**。

**前端兜不住**：页面头部规则名来自接口，会显示成从未实现的那一半，与结论卡讲的「早上 6 点开机」对不上。要么改规则名，要么把降幅那半实现出来拆成两条。

### E. `resultMd` 的判定表存在错误标记 【高】

**BB-S1**：第 2 行温差的 ✅/❌ 三窗口错了两个（`mild=False` 标 ✅、`mild=True` 标 ❌，且两个 `False` 窗口标法还不一致）。判决本身正确（`early && mild`）。

**后果**：第 ③ 块（前端按布尔出）与第 ④ 块（渲染 `resultMd` 原文）会互相打架，读者会以为页面坏了。

### F. D 类缺 `metrics.algo`，且 `maxMeanRatio` 同名不同义 【中】

C06 与 C04 同为 `type: "distribution"`，`metrics` 字段名逐个相同，但：

| | C06（CR0025） | C04（CR0024） |
|---|---|---|
| `maxMeanRatio` 实为 | **max / min**（实测 4.46，而 max/mean 是 1.97） | **max / mean** |
| `ratioThreshold` | 1.3 | 1.2 |
| 判据 | `1.30 < R < 100` 触发 | `CV < 0.15` **且** `R < 1.20` 触发 |
| 方向 | 比值**大**才触发 | 比值**小**才触发 |
| `cv` | 算了但**不参与**判据 | 参与判据 |

E 类和 C 类都有 `metrics.algo`，D 类没有——**前端只能按 `raw.ruleId` 写死分流，每加一条 D 类规则都要改解析器**。

另：C06 的 `cv` 算出却未接入判据。某窗口 CV 0.1314 低于阈值 0.15（96 个点、41.6–81.9，分布相当集中）却因 max/min 触发。**CV 用全部样本、对单点不敏感，max/min 只用 2 个点，改用 CV 判会稳健得多。**

### G. 多条规则把「设备没开」的时段算成「设备表现」 【中，但已累计 9 次】

| 规则 | 表现 |

代码注释已写明：**不要「顺手修正」`eH`/`eL`，那会把判据搞坏。** 请定位这个 4 倍从何而来（疑似 15 分钟采样被当作小时值累加），并说明 `eH`/`eL` 与 `hourlyProfiles` 的单位关系。

### Z. BF-S1 的曲线标签不能套用 DayPairResidual 的正则（前端已规避，记录备查）

`selectionReason` 形如 `"高负荷08-09/低负荷06-01"`。DayPairResidual 用的正则取整串的非数字前缀，会取出「高负荷」并贴到 `holiday` 曲线上，**正好标反**。

曲线归属已用 `Σworkday×4 ≈ eH` 核实：`workday ↔ dateFrom ↔ 高负荷日`。前端改为按 `/` 切段后各取前缀。建议后端在 payload 里显式给出两条曲线的名称与日期，不要让前端从字符串反推（K 里 AA-S2/BA-S2 同类问题）。
